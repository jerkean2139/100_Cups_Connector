04 · Common Questions

You're going to wonder about these.

Tap any question to expand the answer. We'll cover most of these during the demo too.

Do I need to know how to code? +

No. The whole point of what you're seeing is that you describe what you want in plain English, and Claude writes the code. You'll read code on screen during the demo, but reading is different from writing. You don't need to understand every line. You just need to know what you wanted built and whether it does that thing.

If you can write a clear email describing what you want, you can do this.

What if I don't have a meeting transcript? +

Then start with anything else: a voice memo you talked into your phone, a brain dump you typed into Notes, even a few bullet points. The mining prompt works on any text, meetings are just a common starting point because that's where ideas usually come up.

If you have nothing? Just describe your idea in plain English to the planning skill directly. Skip Part One.

Will I really have a working app at the end? +

Yes, a working version of the core idea, often called an MVP. It won't have every feature you ever dreamed of. The planning step deliberately cuts a lot of features out, because trying to build everything at once is how projects fail.

What you'll have is something real, deployed, and demonstrable. From there, you can ask Claude to add features one at a time.

What's the difference between this and ChatGPT? +

ChatGPT will help you build everything you ask for. Claude Code, especially with a planning skill running on top, will tell you when you're trying to do too much.

That pushback is the difference between "I tried to vibe code and it was a mess" and "I tried to vibe code and I have something working." The skill we're using has a built-in scope guard. It calls things out. ChatGPT, by default, doesn't.

Is this safe? Can the AI break my computer? +

The browser version of Claude Code runs on Anthropic's servers, not yours. It can't touch your computer. Each session runs in an isolated virtual machine that gets destroyed after.

The only thing it touches that's yours is your GitHub repository, and you control what permissions it has there. If you're nervous, start by giving it access to a brand new test repository where there's nothing to break.

What happens after the demo ends? +

Three things. First, you'll have a link to this page, bookmark it. Second, you can download the meeting-mining prompt, the planning skill, and the build prompt right at the bottom. Third, anyone who builds something this week using the kit can send it to me. I'm keeping a list of what people make.

The goal isn't for you to remember what I did. It's for you to do it yourself.

What if my idea isn't a tech product? +

Most of the people I work with aren't tech founders. They have coaching practices, real estate businesses, agencies, podcasts. The kind of apps you'll want to build are usually small, internal tools, a contact tracker, a follow-up system, a content organizer, a custom dashboard.

Big tech-founder-style apps are not the right starting point. Tools that make your existing business 10% smoother are. Start there.

01 · Why Go Local

The browser version has tradeoffs.

Claude Code on the web is brilliant for a 60-minute demo. For real work, you'll hit walls. Here's the honest comparison.

Browser · claude.ai/code

Great for:

  • Getting started fast
  • Demos and small experiments
  • Working from any machine
  • Skipping local install

Limits:

  • Sessions run in sandboxed VMs that get destroyed
  • No local file editing across sessions
  • Limited offline capability
  • No custom MCP servers or local tooling
  • Network access restricted by default
Terminal · claude CLI

Great for:

  • Multi-session projects with persistent state
  • Local databases (Docker Postgres, Redis)
  • Custom skills, MCP servers, hooks
  • Serious deployments with CI/CD
  • Working offline on a plane
  • Playwright tests against local builds

Tradeoff:

  • Requires Node.js install
  • You manage your own environment
  • The --dangerously-skip-permissions flag exists. Don't use it lightly.
The hybrid play

You don't have to pick. Use the browser version for ideation and quick experiments. Use the CLI version for production work. Claude Code supports /teleport to move sessions between them.

04 · Permission Modes

The "click allow 109 times" problem.

By default, Claude Code asks permission for every file edit and bash command. For a serious build session, you want fewer interruptions — without going completely off-leash.

Default Mode

Asks every time

Claude prompts you before editing files or running bash commands. Great for first projects. Painful for builds with 50+ steps.

claude
Recommended for serious work

acceptEdits mode

Auto-approves file edits and common bash commands like mkdir, npm, git. Risky commands like sudo still prompt. Best balance of speed and safety.

claude --permission-mode acceptEdits
Power user

Custom allowlist

Define exactly which tools auto-approve in .claude/settings.json. The professional way. Allowlist what you trust, denylist what you fear.

A word about --dangerously-skip-permissions

This flag exists. It auto-approves everything. It's also why people accidentally rm -rf ~/. Don't reach for it unless you're working in a throwaway VM or container. acceptEdits with a denylist gives you 95% of the convenience with 5% of the risk.

The settings.json this project uses

Drop this file at .claude/settings.json in your project root. Combined with --permission-mode acceptEdits, you get a build session that runs without nagging but still blocks the dangerous stuff.

{
  "permissions": {
    "defaultMode": "acceptEdits",
    "allow": [
      "Bash(npm:*)", "Bash(npx:*)", "Bash(node:*)",
      "Bash(git:*)", "Bash(railway:*)",
      "Bash(mkdir:*)", "Bash(touch:*)", "Bash(mv:*)",
      "Bash(cp:*)", "Bash(rm:*)",
      "Bash(playwright:*)", "Bash(npx playwright:*)",
      "Read", "Write", "Edit", "Glob", "Grep"
    ],
    "deny": [
      "Bash(rm -rf /:*)", "Bash(rm -rf ~:*)",
      "Bash(sudo:*)",
      "Bash(curl * | sh:*)", "Bash(curl * | bash:*)"
    ]
  }
}

The full file is in the kit download.

Local · Claude Code + a clean project folder

REQUIRED · ~3 MIN
3 MIN
+

Claude Code lives in a single project folder on your machine. Everything happens here — edits, git commands, test runs. Get this right once, every project starts the same way.

Create a fresh project folder under your home directory
A clean folder per project keeps Claude's context window focused — it doesn't accidentally read files from a sibling project. Use a consistent path like ~/projects/ so you always know where things live.

This file solves the "click allow 109 times" problem. It tells Claude Code which bash commands are safe to run without prompting (npm, git, mkdir) and which to always confirm (sudo, rm -rf). Without this, every build step interrupts you.

Initialize git immediately — checkpoint before you write code
Always git init before anything else. Even before npm install. This gives you an empty initial commit you can rewind to if Claude Code's first run goes sideways. The .gitignore prevents secrets and bloat from ever entering version control.
git init
echo "node_modules
.env
.DS_Store
dist
.railway" > .gitignore
Three lines of setup. After this, every project you start opens the same way and Claude knows exactly where the rails are.
02

Remote · GitHub as source of truth

REQUIRED · ~3 MIN
3 MIN
+

Code lives on GitHub. Two long-lived branches. main is what users see. staging is where you break things safely.

Create the GitHub repo from the command line (or web UI)
The gh CLI is faster than clicking through github.com but the web UI works too. Either way, what matters is starting private — public-by-default lets you accidentally leak secrets you forgot were in your commit history.
gh repo create your-project --private --source=. --remote=origin
Push initial commit to main, then create the staging branch
The first push establishes main as the default. Creating staging from main means both branches start identical. From here forward, all work happens on staging. Main only receives merges of verified code, never direct pushes.
git add .
git commit -m "init"
git push -u origin main
git checkout -b staging
git push -u origin staging
Set staging as your default working branch in your local checkout
Cleanest mental model: staging is for breaking things. Main is what users see. If you stay on staging by default, you literally cannot push broken code to production by accident. Promotion to main is always a deliberate merge.
git checkout staging  # always start work here
Two branches, one rule: never push directly to main. Promotion is always a merge from staging.
03

Deploy · Railway with two environments

REQUIRED · ~5 MIN
5 MIN
+

Railway watches your GitHub repo. Main branch auto-deploys to production. Staging branch auto-deploys to staging. Separate environments, separate databases. Zero manual deploys.

Initialize the Railway project and create a staging environment
Railway environments are full isolation — separate database, separate env vars, separate URL. This is what makes "verify on staging before promoting to main" actually safe. Your test data doesn't pollute production.
railway init your-project
railway environment new staging
Connect each Railway environment to its GitHub branch in the dashboard
In Railway's UI: production environment → main branch, staging environment → staging branch. Once wired, every git push triggers an automatic build and deploy. You never touch a deploy button again.
Set environment variables separately for each environment
Production secrets and staging secrets must be different. Production hits real APIs and real databases; staging should hit test versions. Never share secrets between environments — staging credentials get exposed more often (test users, screenshots, debug sessions) and you don't want production blast radius.
Push staging branch → staging deploys. Merge to main → production deploys. Two environments, two URLs, zero manual deploy steps.
04

Snapshot · the nightly parachute

UPGRADE · ~5 MIN
5 MIN
+

A nightly GitHub Action cuts a read-only backup branch from main. If something goes sideways, you have insurance. Parachute, not merge candidate.

Create the workflow file at .github/workflows/nightly-backup.yml
GitHub Actions runs this on a cron schedule with no infrastructure to maintain. The workflow_dispatch trigger also lets you manually fire it from the GitHub UI when you want a snapshot before a risky change. Cost: zero — public/private repos both get free Action minutes.
name: Nightly Backup Branch
on:
  schedule:
    - cron: '0 3 * * *'  # 03:00 UTC daily
  workflow_dispatch:

jobs:
  snapshot:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          ref: main
          fetch-depth: 0
      - name: Create snapshot branch
        run: |
          DATE=$(date +%Y-%m-%d)
          git checkout -b "backup/$DATE"
          git push origin "backup/$DATE"
Treat backup branches as read-only — never merge them back
A backup branch is insurance, not a feature branch. If you merge backup/2026-05-06 back into main, you'd undo everything done since that date. Wrong move. Right move: checkout the backup, copy out the file you need, switch back to staging, paste it in, commit normally.
# Recover one file from a snapshot
git checkout backup/2026-05-06 -- path/to/lost-file.ts
git checkout staging
Add a cleanup job to delete backup branches older than 30 days
Without cleanup, you accumulate 365 backup branches a year and your repo gets bloated. A separate weekly Action that deletes backup/* branches older than 30 days keeps things tidy. Or use git tags instead of branches if you don't need them browseable in the GitHub UI.
Two-line GitHub Action gives you 30 days of recovery insurance. Costs nothing. Saves you the one time you really need it.
05

Docker · local Postgres for offline dev

SKIP IF NEW · ADD LATER
SKIP OK
+
First project? Skip this whole section.

You don't need Docker to get a working app deployed. Layers 1-4 are enough. This layer is a quality-of-life upgrade for your second or third project, when you start running into real reasons to want a local database (working offline, not waiting on Railway, keeping test data separate from code). If you're brand new, scroll past this and come back when something here actually solves a problem you're hitting.

Docker Desktop runs your local Postgres in a container. Your data lives separately from your code, surviving repo wipes and re-clones. Bonus: you can develop on a plane.

Spin up Postgres in a named container with a persistent volume
The -v my-data:/var/lib/postgresql/data flag is the trick. That named volume persists across container restarts and even container deletions. You can blow away your project folder, re-clone, and your test data is still there. Your data is safer than your code.
docker run --name my-pg \
  -e POSTGRES_PASSWORD=dev \
  -p 5432:5432 \
  -v my-data:/var/lib/postgresql/data \
  -d postgres:16
Wire your local app to the container with a DATABASE_URL in .env
Your code uses one DATABASE_URL variable. Locally it points to localhost:5432 (the Docker container). On Railway it points to Railway's managed Postgres. Same code, different env. The .env file is gitignored so secrets never travel.
echo "DATABASE_URL=postgresql://postgres:dev@localhost:5432/postgres" >> .env
Stop and restart the container without losing data
Containers are ephemeral, volumes are not. Stopping and starting the container is fine. Even docker rm only kills the container — the named volume persists. To actually wipe data, you'd have to docker volume rm my-data deliberately. That separation is the safety net.
docker stop my-pg
docker start my-pg     # data still there
docker rm my-pg        # container gone, data still there
docker run ... my-pg   # recreate, attach to volume, back to normal
Code and data live in different boxes. You can break either one without losing the other.

07 · Tests as Policy

Encode your guardrails as tests.

The most important constraint in a build is the one that's enforced. Tests are how you enforce.

The 100 Cups Connector PRD includes a "Byron Rule" test that verifies tasks never auto-send. If a future change breaks that constraint, the test fails and CI blocks the deploy. That's how you turn a verbal commitment into permanent infrastructure.

// tests/e2e/task-gate.spec.ts
test('approving a task triggers send, not before', async ({ page }) => {
  // 1. Create a contact via API
  // 2. Generate a follow-up task
  // 3. Verify task is in DB with status='pending'
  // 4. Verify GHL endpoint NOT called yet
  expect(mockGhl.callCount).toBe(0);

  // 5. Tap "Approve & Send"
  await page.click('[data-testid="approve-task"]');

  // 6. Verify GHL endpoint called exactly once
  expect(mockGhl.callCount).toBe(1);
  expect(taskStatus).toBe('sent');
});
→ If you're building any AI tool that takes outbound action — emails, posts, payments — a test like this is non-negotiable. Voluntary policies erode. Tests don't.

Run on every commit

Add a GitHub Action that runs Playwright on every push. If tests fail, the deploy blocks.

name: Test
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
      - run: npm ci
      - run: npx playwright install --with-deps
      - run: npx playwright test
08 · Tips From the Trenches

Things that actually matter.

Use Plan Mode for big changes

Before letting Claude Code make sweeping changes, run claude --permission-mode plan. In plan mode, Claude only reads files and explores — it can't write anything. Once you're satisfied with the plan, switch modes or hand it off.

Teleport between web and CLI

Started a session in claude.ai/code? You can pull it into your terminal with /teleport. Useful when an experiment outgrows the browser sandbox.

Skills compose

Multiple skills can apply to one task. Drop the idea-to-prd skill alongside frontend-design, repo-pentest, or your own custom skills. Claude reads them all and routes appropriately.

MCP servers extend everything

The CLI version supports MCP (Model Context Protocol) servers — connect Claude Code to your existing tools (Slack, Linear, custom internal APIs). The browser version is more sandboxed; this is a CLI-exclusive advantage.

Hooks for automation

Claude Code supports hooks that fire on events (before commit, after edit, etc.). Use them for auto-formatting, lint-on-save, or running specific tests when specific files change.

09 · Common Issues

What goes wrong, and how to fix it.

"command not found: claude"

Restart your terminal after install — npm global binaries need a fresh PATH. If still broken, check npm config get prefix and add $(npm config get prefix)/bin to your PATH.

Claude Code stops mid-build

Type continue and hit Enter. It picks up where it left off. If you hit a context-window error, ask for a summary and start a fresh session with that summary.

Permission errors on macOS

If you see EACCES errors during npm install, don't use sudo. Set up a user-owned npm prefix instead: npm config set prefix ~/.npm-global and add that to your PATH.

Railway deploy succeeds but app is broken

90% of the time it's missing environment variables. Run railway variables to check what's set. Compare against your local .env.example.

Playwright tests pass locally, fail in CI

Usually a timing issue. Replace page.waitForTimeout with proper page.waitFor* assertions. Or it's a missing system dependency — run npx playwright install --with-deps in your CI workflow.

Backup branch is huge

If backup/YYYY-MM-DD branches accumulate over months, they bloat your repo. Add a cleanup workflow that deletes branches older than 30 days. Or use git tags instead of branches if you don't need them browseable.
